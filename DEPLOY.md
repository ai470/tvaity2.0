# Деплой 2.tvaity.ru

Команды выполняются на сервере `111.88.251.214` от root.

```bash
cd /var/www/tvaity2.0
bash deploy/deploy.sh
```

Скрипт сам получает `origin/main`, обновляет чистую рабочую копию через
`git merge --ff-only`, готовит отдельный релиз и переключает симлинк `current`.
При локальных изменениях или расхождении веток он останавливается, не удаляя правки.
`git reset --hard`, ручной `chown` и перезапуск Nginx для обычного деплоя не нужны.
Простой `git pull` теперь обновляет только исходники; для публикации нужен скрипт выше.
JS/CSS в HTML короткого лендинга и `/sps/` получают версию по хешу содержимого.
Браузер проверяет актуальность ресурсов, поэтому старый кеш не смешивается с новой разметкой.

## Какие каталоги за что отвечают

| URL | Источник | Публикация |
| --- | --- | --- |
| `/reg-short/` | `short-land/` из этого репозитория | `/var/www/tvaity2.0-deploy/current/reg-short/` |
| `/sps/` | `sps/` из этого репозитория | `/var/www/tvaity2.0-deploy/current/sps/` |
| `/reg/`, `/reg-01/` | копия отдельного экспорта + исправление UTM | `/var/www/tvaity2.0-deploy/current/legacy/` |
| `/_next/`, остальные старые страницы | отдельный экспорт Next.js | `/var/www/2.tvaity.ru/` (исправленный JS виджета берётся из релиза) |

Старого сайта нет в этом репозитории. Не копировать поверх него `short-land/`,
не направлять на него `rsync --delete` и не менять общий `root` на короткий лендинг.
Деплой проверяет контрольные суммы старого сайта до и после публикации.
Отдельный деплой старого Next.js-сайта следует выполнять вне времени этого деплоя.

### Исправление UTM в старой сборке

На сервере нет исходников `/reg` и `/reg-01`, только статический экспорт Next.js.
`deploy/prepare_legacy.py` копирует эти два маршрута в релиз и заменяет только
генератор URL виджета в известном JS-бандле. Он использует тот же `gc-tracking.js`,
что и короткий лендинг. Новый бандл получает имя с хешем; ссылки обновляются
в HTML и RSC-файлах. Оригинальная выгрузка остаётся неизменной.

Скрипт сверяет SHA-256 оригинального бандла и останавливается при его изменении.
После обновления старого Next.js-сайта нужно пересмотреть эту временную правку
или перенести helper в найденные исходники и удалить подмену. Не отключать
проверку хеша вслепую. Переключение/откат всех трёх лендингов выполняется вместе.

Проверка URL-helper: `node --test tests/gc-tracking.test.cjs`.

## Проверки и откат

`deploy/nginx.conf` — конфигурация только виртуального хоста `2.tvaity.ru`.
При её изменении скрипт сохраняет предыдущую версию, выполняет `nginx -t` и
делает `reload`. Сертификаты не выпускаются заново при деплое.

После переключения проверяются `/reg/`, `/reg-01/`, `/reg-short/`, `/sps/`,
корень сайта, локальные CSS/JS/изображения/шрифты/PDF, содержимое ответов,
редиректы с UTM и HTTPS. Проверка выполняется через localhost с правильным SNI
и через публичный DNS. Отсутствующие файлы должны возвращать 404, а не HTML с 200.
Формы не отправляются. При ошибке восстанавливаются прежний релиз и конфигурация.

Ручная проверка текущего прода:

```bash
python3 /var/www/tvaity2.0/deploy/verify.py
nginx -t
```

Релизы находятся в `/var/www/tvaity2.0-deploy/releases/`, резервные копии
конфигурации и путь предыдущего релиза — в `/var/backups/tvaity2-deploy/`.
Путь последней успешной копии записан в `/var/www/tvaity2.0-deploy/last-backup`.
Релизы автоматически не удаляются.

Чтобы откатить содержимое после успешного деплоя, верните нужный коммит через
`git revert`, запушьте `main` и снова запустите `bash deploy/deploy.sh`.

## Сертификат и логи

Сертификат: `/etc/letsencrypt/live/2.tvaity.ru/`.
Продлением занимается Certbot по системному таймеру, независимо от Git.
Проверка продления только этого домена:

```bash
/snap/bin/certbot renew --cert-name 2.tvaity.ru --dry-run --no-random-sleep-on-renew
```

Логи этого домена: `/var/log/nginx/tvaity2.access.log` и
`/var/log/nginx/tvaity2.error.log`.
